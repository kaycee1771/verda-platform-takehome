# ADR 0001: Use RKE2

- **Status:** Accepted
- **Date:** 2026-08-16
- **Owners:** Platform architecture
- **Blocking gates:** None for Phase 4; RKE2 `v1.35.7+rke2r1` is compatibility-checked, immutable,
  and live-proven with the selected Rancher release path

## Context

The assignment permits k3s, kubeadm, or RKE2 and asks for Rancher. The cluster must demonstrate quorum, hardening, deterministic lifecycle, failure behavior, and direct access on self-provisioned VMs.

## Decision

Use an exactly pinned RKE2 patch compatible with the selected Rancher release. RKE2 provides embedded etcd, production-oriented security defaults, supported Cilium integration, and a documented three-server HA path.

## Alternatives considered

- **k3s:** lower overhead, but a weaker fit for this Rancher-aligned senior platform exercise.
- **kubeadm:** maximum upstream transparency, but substantially more lifecycle assembly with little assessment benefit.
- **Verda Instant Cluster:** operationally relevant but does not satisfy the intended raw-VM provisioning/Rancher exercise as directly.

## Consequences

- RKE2 version and Kubernetes minor must be selected with the current Rancher support evidence.
- A fixed registration/API endpoint is mandatory and independent from etcd quorum.
- Distribution convenience does not replace host hardening, backup, upgrade, or failure tests.

## Validation evidence

Current RKE2 HA documentation (reviewed 2026-08-16) recommends three server nodes and a fixed registration address. Final acceptance requires three Ready nodes, healthy etcd endpoints/members, a support bundle, DNS/service/CNI tests, and controlled one-node loss.

## Production evolution

For a Verda-managed Kubernetes product, reassess kubeadm, Cluster API, Rancher provisioning, or a custom lifecycle service based on fleet scale, hardware/GPU integration, upgrades, and network ownership.
